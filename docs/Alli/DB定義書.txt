#  データベース定義書

## 1. データベース基本情報

### 1.1 システム概要
本システム「AIスケジュール外出支援サービス」は、外出予定を自然文で入力することで、出発から帰宅までの行動計画を自動生成・提示するAIエージェント型アプリケーションである。主要エンティティは、ユーザー、行動計画、行動項目、スロット評価、AI対話履歴、ルーティン、メモ、カレンダー連携、カレンダー予定キャッシュ、出発検知記録、ポイントプログラムの11個である。

### 1.2 データベース情報
- **DBMS**: 未定
- **文字コード**: UTF-8 (utf8mb4)
- **照合順序**: utf8mb4_general_ci
- **エンジン**: InnoDB（MySQLの場合）

# インデックス定義レビュー結果

## 1. 不足しているインデックス（外部キー対応）

- 対象：calendar_event テーブル／`user_id`、`calendar_integration_id`
  - 指摘内容：外部キー2件（`fk_calendar_event_user_id`、`fk_calendar_event_calendar_integration_id`）に対し、それぞれ単独インデックス（`idx_calendar_event_user_id`、`idx_calendar_event_calendar_integration_id`）が定義されており、外部キーに対応するインデックスは存在する。※不足なし（確認事項として記載）
  - 根拠：「3.9 calendar_event テーブル」「4. 外部キー制約」

- 対象：全テーブルの外部キー制約
  - 指摘内容：「4. 外部キー制約」に列挙された外部キー（plan.user_id、plan_item.plan_id、slot_evaluation.plan_id、agent_session.plan_id、routine.user_id、memo.user_id、calendar_integration.user_id、calendar_event.user_id／calendar_integration_id、departure_log.user_id／plan_id、point_program.user_id）について、いずれも対応するインデックスが「3. インデックス定義」に定義されており、外部キーに対する不足は確認されない。
  - 根拠：「3. インデックス定義」各節と「4. 外部キー制約」の対照

## 2. 一意制約に関する確認

- 対象：user テーブル／`cognito_user_id`、`email`
  - 指摘内容：`cognito_user_id` は「外部サービス連携に必要な属性」、`email` は認証の主体に関わる属性だが、これらに対する UNIQUE インデックスが定義されていない。一方、カラム定義上はいずれも NOT NULL であり、一意性を担保するインデックスが存在しない。
  - 根拠：「2.1 user テーブル」（cognito_user_id・email は NOT NULL）、「3.1 user テーブル」（PRIMARY のみ定義）
  - ※ただし「一意であるべき」との明示的記述は入力内に無いため、一意制約要否は定義書上の情報からは断定不可。

## 3. 複合インデックスのカラム順序

- 対象：idx_memo_user_id_created_at（memo／`user_id, created_at`）
  - 指摘内容：説明に「ユーザー別・作成日時での絞り込み／自動削除用」とあり、先頭カラムが `user_id`。memo は「作成から1週間で自動削除」される仕様があるが、自動削除は `created_at` 単独での範囲検索を要する可能性がある一方、本複合インデックスの先頭カラムは `user_id` である。カラム順序の明らかな不整合とまでは断定できないが、用途（自動削除）と先頭カラム（user_id）の整合性に留意が必要。
  - 根拠：「2.7 memo テーブル」説明、「3.7 memo テーブル」

## 4. 重複・冗長・過剰なインデックス

- 指摘事項なし（同一カラム構成の重複、先頭カラムの包含関係による冗長、同一カラムへの重複定義は確認されない）
  - 根拠：「3. インデックス定義」各節

## 5. 命名規則の不統一

- 対象：全インデックス名
  - 指摘内容：
    - 通常インデックスは `idx_{テーブル名}_{カラム名}` 形式で統一されている。
    - UNIQUE インデックスは `uq_{テーブル名}_{カラム名}` 形式（`uq_calendar_integration_user_id_provider`）。
    - PRIMARY は `PRIMARY` で統一。
    いずれも接頭辞による種別区別が一貫しており、明らかな命名規則の不統一は確認されない。
  - 根拠：「3. インデックス定義」各節

## 補足（確実な指摘のまとめ）

入力情報のみを根拠として「明確に問題」と断定できる指摘は以下のとおりです。

- user テーブルの `cognito_user_id`／`email`：NOT NULL かつ外部サービス連携・認証に関わる属性でありながら UNIQUE 制約・インデックスが未定義（ただし「一意であるべき」との明示記述は入力内に存在しないため、要否の最終判断は定義書からは不可）。

上記以外の観点（重複・冗長・過剰インデックス、外部キー対応インデックスの不足、複合インデックスの明らかな順序不整合、命名規則の不統一）については、入力に明示された情報の範囲で明確な問題は確認されませんでした。
