# 第1章 システムの目的・概要
 
## 1.1 システムの概要
 
本システム「AIスケジュール外出支援サービス」は、ZDCの自社案件として、ソリューション第二開発部（SOL2）が企画・開発するAIエージェント型の外出行動計画支援アプリケーションである。ユーザーが外出の予定を自然な文章で入力するだけで、家を出てから帰宅するまでの一連の行動計画（出発時刻、乗換経路、駅の出口、徒歩・自転車・車ルート、立ち寄る店舗、帰宅までの導線）を一括で自動生成し、地図とともに提示することを目的とする。
 
本システムの中核となる価値は、外出前の準備や時間の逆算にかかる心理的負担の軽減にある。従来、ユーザーは時刻表・乗換案内・店舗情報を個別に調べ、準備時間や移動時間を自ら逆算する必要があった。これに対し本システムは、一文の入力から当日の行動計画を得られるようにすることで、スケジューリングの煩わしさから利用者を解放し、準備・移動時間の見積もり誤りによる遅刻や用事の失念を防ぐことを狙いとする。
 
主要機能として、テキストによる用事の入力・確認質問、行動計画の組み立て、出発時刻・移動ルートの算出、立寄り先の順序最適化、優先条件設定、地図表示、詳細表示の段階的開示、カレンダー連携（Google／Outlook）、ルーティン、メモ・買い物リスト、店舗優先選定（ポイントプログラム含む）、アカウント・設定管理を提供する。また、準備時間学習のための出発検知（自宅ジオフェンス退出検知）を実装する。音声入力、出発アラート、プッシュ通知、運行情報監視といった低優先度機能は本リリースでは実装準備のみ（スタブ／Feature Flag OFF）とし、将来フェーズでの有効化に備える。
 
本システムのAIエージェント方式は、検討すべき項目の一覧をプログラムが管理し（行動計画テンプレート上の全スロットを網羅評価する構造）、各項目の判断・内容の決定をAIが担うという二層構造を特徴とする。これにより、AIがスロット検討そのものを省略できない仕組みを担保しつつ、ユーザー入力・カレンダー・ルーティン・外部サービス結果を踏まえた柔軟な計画生成を実現する。
 
提供形態は、単一のFlutterコードベースからiOS（App Storeネイティブアプリ）、Android（Google Playネイティブアプリ）、Windows（ブラウザ上のWebアプリ）の3プラットフォームへビルドする。想定ユーザーは、外出前の準備や時間の逆算に苦手意識があり行動計画を立てること自体が負担になっている人、遅刻や物忘れが起きやすい人、外出の合間に買い物や用事を効率よく済ませたい人であり、日本国内・日本語利用者を前提とする。同時アクティブユーザーは数人〜数十人規模を想定し、契約可能な最小のAWSリソースで運用する。課金・決済機能はスコープ外であり、無料で提供する。

## 1.3 ユースケース
 
本システムのアクターは、一般利用者であるエンドユーザーと、AI推論・地図・乗換案内・カレンダー等を提供する外部サービス群である。管理者向けの専用機能は本リリースでは設けず、監視はCloudWatch Alarmsによる通知のみで運用する。
 
エンドユーザーは、まずCognitoによる認証（サインアップ／サインイン、パスワードリセット）を行い、初回は6ステップのオンボーディングウィザードで自宅・駅・徒歩速度・優先条件・カレンダー連携・同意等の初期設定を行う。認証後は、ホーム画面で用事を自然文のテキストで入力し、必要に応じてAIからの確認質問（最大2回）に回答したうえで行動計画の生成を依頼する。生成された行動計画は、地図とタイムラインで確認でき、段階的開示による詳細展開、用事の修正（revise）や行動項目の削除・再評価が可能である。さらにエンドユーザーは、ルーティンの登録・編集・削除・単発スキップ、メモ・買い物リストの作成・編集・削除・チェック、店舗優先選定のためのポイントプログラム設定、カレンダー連携の開始・解除、プロファイル・優先条件・プライバシー設定の管理、全端末ログアウトや退会といったアカウント操作を行える。iOS／Androidでは自宅ジオフェンスの退出による出発検知が動作し、準備時間学習に用いられる。音声入力・残り時間表示・延期再計画・プッシュ通知・通知設定の実配信は本リリースでは準備のみで、UI入口やAPI骨格のみが提供される。
 
外部サービスは、AI連携基盤・APIサービスからの要求に応じて機能を提供する。Amazon Bedrock Claudeは自然文解析・意図抽出・確認質問・候補選定を、Google Maps Platformはジオコーディング・場所検索・ルート算出・地図描画を、乗換案内APIは乗換経路・駅出口・乗車位置を、Google Calendar API／Microsoft Graph APIは当日予定を、Amazon Cognitoは認証を担う。
 
```mermaid

    Ext[外部サービス]
 
    subgraph "System - AIスケジュール外出支援サービス"

        UC1[認証・オンボーディング]

        UC2[用事入力・確認質問]

        UC3[行動計画生成・確認]

        UC4[計画修正・項目削除]

        UC5[ルーティン・メモ管理]

    end
 
    User --> UC1

    User --> UC2

    User --> UC3

    User --> UC5

    User --> UC6

    User --> UC7

    UC3 --> Ext

    UC1 --> Ext

```
 
## 1.4 業務フロー
 
### 認証・オンボーディング
 
エンドユーザーはメールとパスワードでサインアップ／サインインを行う。Amplify Flutterを通じてCognitoが認証しJWTを発行する。初回利用時は6ステップのオンボーディングウィザードに進み、Step1で自宅（必須）、Step2で駅（任意）、Step3で徒歩速度と準備時間（初期値あり）、Step4で優先条件（初期値あり）、Step5でカレンダー連携（任意）、Step6で各種同意（必須）を設定する。ログイン失敗によるアカウントロックはなく、無操作1日でセッションが終了する。
 
```mermaid

flowchart LR

    A[サインアップ/サインイン] --> B[Cognito認証・JWT発行]

    B --> C{初回利用}

    C -->|はい| D[オンボーディング6ステップ]

    C -->|いいえ| E[ホーム画面]

    D --> E

```
 
### 行動計画生成
 
エンドユーザーがホーム画面で用事を自然文で入力すると、AI連携基盤が意図解析を行い、スロット評価テンプレートに基づき全スロットをMAIN → OUTBOUND → DEPARTURE → RETURNの順で評価する。必須情報が読み取れない場合は確認質問をホーム画面内インラインで表示し、最大2回まで回答を受け付ける。上限到達後も情報が確定しない場合は妥当な仮定を置き、その旨を明示して生成を続行する。生成時にはBedrockによる判断に加え、Google Maps・乗換案内API・カレンダーAPIの結果と整合性を検証したうえで、出発時刻・移動ルート・立寄り先の順序・帰宅までの導線を組み立て、地図とタイムラインで提示する。
 
```mermaid

flowchart LR

    A[自然文入力] --> B[意図解析・スロット評価]

    B --> C{必須情報充足}

    C -->|不足| D[確認質問 最大2回]

    D --> C

    C -->|充足/上限到達| E[外部サービス照会・整合性検証]

    E --> F[行動計画組立]

    F --> G[地図・タイムライン提示]

```
 
### 計画修正・出発検知
 
提示された行動計画に対し、エンドユーザーは自然文またはUI操作による用事の修正（revise）や行動項目の削除・再評価を行える。当日、iOS／Androidでは自宅ジオフェンスからの退出が検知されるとDepartureLogに実績が記録され、準備時間学習に用いられる。出発検知は再計画のトリガーではなく、実績記録のみを目的とする。延期申告に応じた再計画や運行情報変化による自動通知は本リリースでは準備のみである。
 
```mermaid

flowchart LR

    A[行動計画] --> B{ユーザー操作}

    B -->|修正/削除| C[revise再生成]

    C --> A

    B -->|外出| D[ジオフェンス退出検知]

    D --> E[DepartureLog記録]

    E --> F[準備時間学習]

```
 
### メモ・ルーティン管理
 
エンドユーザーはルーティンを登録・編集・削除でき、当日不要な場合は単発スキップが可能である。登録されたルーティンは行動計画生成時にイベントスロットとして反映される。メモ・買い物リストは付箋形式で作成・編集・削除・チェックができ、オフライン時はローカルに一時保存され復帰時に同期される。メモは作成から1週間で日次バッチにより自動削除される。
 
```mermaid

flowchart LR

    A[ルーティン/メモ操作] --> B[Aurora保存]

    B --> C[行動計画生成へ反映]

    B --> D[1週間経過メモ 日次削除]

```
 
## 1.5 システム構成図
 
本システムは、単一のFlutterコードベースから構築されるiOS／Android／Windows Webの各クライアントと、AWS東京リージョン上に構築するサーバーサイドで構成される。iOS／AndroidはALBへJWT付きで直接通信し、Windows WebはCloudFront経由で接続する（静的資産はS3から配信し、api／agentはALBへ振り分ける）。サーバーサイドはECS Fargate上の単一サービスで稼働し、業務データを扱う`/api/*`のAPIサービス群と、AI推論を伴う`/agent/*`のAI連携基盤API群をパスベースで振り分ける。加えて、メモ削除・運行監視・段階通知の各バッチを備える。データストアはAurora Serverless v2 PostgreSQLに一本化し、DynamoDBは使用しない。認証はAmazon Cognito User Poolが担い、JWT検証はアプリ層ミドルウェアで実施する。AI推論はAmazon Bedrock Claude、地図・ルートはGoogle Maps Platform、乗換案内は乗換案内API、カレンダーはGoogle Calendar／Microsoft Graph、プッシュ通知はAmazon SNS（準備のみ）と連携する。

### 2.2.1 ログイン／初回オンボーディング画面
 
**利用対象**

一般利用者（エンドユーザー）
 
**機能概要**

Amazon Cognito User Poolを用いたメール＋パスワード認証によるサインアップ／サインインを行う画面。新規ユーザーはサインアップ後、全6ステップの初期設定ウィザードで自宅・駅・徒歩速度・優先条件・カレンダー・同意を設定する。
 
**処理フロー**

1. ユーザーがサインイン（メール／パスワード）またはサインアップを選択する。

2. サインアップの場合、確認コード入力を経てアカウントを有効化する。

3. 初回ログイン時、6ステップの初期設定ウィザードを表示する。

4. Step1（自宅）・Step6（同意）を必須入力、Step2・5を任意、Step3・4を初期値で進行する。

5. 全ステップ完了後、ホーム画面へ遷移する。
 
**画面構成概要**

上部にウィザード進捗バー（例「3/6」）を配置し、サインイン／サインアップ切替タブ、入力フォーム、ステップごとの設定領域、次へ／戻るボタンを配置する。エラーは入力欄直下にインライン表示する。

### 2.2.2 ホーム／入力画面（確認質問インライン含む）

一般利用者（エンドユーザー）
 
**機能概要**

## 2.3 処理一覧・処理詳細
 
### 2.3.1 処理一覧
 
本システムで定義する種別「処理」（バッチ処理・非同期処理・検知処理等）を以下に整理する。
 
| カテゴリ | 処理名 | 処理概要 | 実行タイミング |

| --- | --- | --- | --- |

| データ保守 | メモ自動削除バッチ | 作成から1週間経過したメモを日次で自動削除する | 日次 |

| 位置情報・検知 | 出発検知記録処理 | 自宅ジオフェンス退出を検知し、DepartureLogに実績を記録する（準備時間学習用） | リアルタイム（iOS／Android） |

| 運行監視 | 運行情報監視バッチ | 運行情報等を定期監視し計画への影響を検知する（Feature Flag OFF・準備のみ） | 定期（EventBridge Scheduler） |

| 通知 | 出発アラート段階通知バッチ | 出発-30/-15/-5/0分の4段階通知をスケジュール登録・配信する（Feature Flag OFF・準備のみ） | スケジュール登録型（準備のみ） |
 
※上記のうち「実装」区分は「メモ自動削除バッチ」「出発検知記録処理」の2件。「運行情報監視バッチ」「出発アラート段階通知バッチ」は準備のみ（スタブ／Feature Flag OFF）。
 
---
 
### 2.3.2 処理詳細
 
#### 2.3.2.1 メモ自動削除バッチ
 
**処理概要**

作成から1週間（7日）を経過したメモを日次バッチで検出し、Auroraから自動削除する。メモから抽出した品目は永続化しないため対象外とする。
 
**処理フロー**

1. 日次のスケジュール起動により処理を開始する。

2. Auroraのメモテーブルから、作成日時が現在日時から1週間以上経過したメモを抽出する。

3. 抽出したメモを削除する。

4. 処理結果（削除件数等）をCloudWatch Logsへ出力する。
 
---
 
#### 2.3.2.2 出発検知記録処理
 
**処理概要**

自宅ジオフェンスからの退出を検知し、出発検知記録API（POST /agent/plans/{planId}/departure-detected）を通じてDepartureLogへ実績を記録する。準備時間学習用であり、再計画のトリガーではない。対象はiOS／Androidのみ（Windows Webは対象外）。位置情報は準備時間学習のみに使用し、常時位置の送信・保存は行わない。
 
**処理フロー**

1. クライアント（iOS／Android）で自宅ジオフェンスの退出イベントを検知する。

2. 出発検知記録APIを呼び出す。

3. サーバー側で該当計画に対する出発実績（退出時刻等）をDepartureLogへ記録する。

4. 記録結果を準備時間学習用データとして蓄積する（再計画は行わない）。
 
---
 
#### 2.3.2.3 運行情報監視バッチ（準備のみ）
 
**処理概要**

運行情報等を定期監視し、遅延・運休等による計画への影響を検知する処理。本リリースはEventBridgeの骨格のみ用意し、Feature Flag OFF（本体処理は無効）とする。
 
**処理フロー**

1. EventBridge Schedulerによる定期起動で処理を開始する（Feature Flag ONの場合のみ本体実行）。

2. 運行情報APIを参照し、対象計画に影響する遅延・運休等を検知する（準備のみ・スタブ）。

3. 影響検知時はプッシュ通知連携へ引き渡す想定のインターフェースを保持する（本リリースでは配信しない）。
 
※本リリースではスタブ動作確認のみを対象とする。
 
---
 
#### 2.3.2.4 出発アラート段階通知バッチ（準備のみ）
 
**処理概要**

出発予定時刻を基準に、-30分／-15分／-5分／0分の4段階通知をスケジュール登録・配信する処理。本リリースはEventBridge Scheduler骨格のみ用意し、Feature Flag OFF（配信は行わない）とする。
 
**処理フロー**

1. 計画確定時に、出発予定時刻を基準とした4段階（-30/-15/-5/0分）の通知スケジュールを登録する（準備のみ）。

2. 各スケジュール時刻の到来を契機に通知配信処理を起動する想定のインターフェースを保持する（本リリースでは配信しない）。

3. プッシュ通知（Amazon SNS）連携へ引き渡す想定のインターフェースを保持する（Feature Flag OFF）。
 
※本リリースではスタブ動作確認のみを対象とし、実配信はスコープ外（将来フェーズで有効化）。

## 3.4 API設計
 
本システムはFlutterクライアント（iOS／Android／Windows Web）とAWSバックエンドが分離した構成のため、クライアント・サーバー間はREST（JSON）APIで通信する。API設計方針を以下に定義する。
 
**API基本方針**

- ECS Fargate上の単一サービス内で `/api/*`（APIサービス群）と `/agent/*`（AI連携基盤API群）をパスベースで振り分ける

- 通信データ形式はJSON、日時はISO 8601形式（例：2026-08-31T10:30:00+09:00）で送受信し、UI表示時にHH:mm形式（24時間制）等へ変換する
 
**主要APIグループ**
 
```

AI連携基盤（agent）	POST /agent/plans/{planId}/revise（計画修正・再生成）	実装

APIサービス（api）	GET /api/calendar/events（カレンダー予定）	実装
```

**エラーハンドリング方針**

- 行動計画生成の日次上限超過時は 429 RATE_LIMITED を返却し、クライアント側でユーザー向けの分かりやすいメッセージを表示する

- API取得失敗時は、クライアント側で該当領域に「取得に失敗しました」＋領域内再試行ボタンを表示する（エラー統一画面は設けない）
 
**確認質問ループの制御**

- 必須情報が読み取れない場合は確認質問を生成するが、上限は1リクエストあたり最大2回とする

- 上限到達後も必須情報が確定しない場合は、妥当な仮定（デフォルト値）を置き、その旨を明示して生成を続行する（無限ループ防止）

- **サービス**：Google Calendar API、Microsoft Graph API（Outlook）

### 4.3.2 AWSサービス間連携
 
**Amazon Bedrock（AI推論）**

- **用途**：自然文解析、意図・制約抽出、確認質問、候補選定

- **連携方式**：AWS SDK（Converse API）

- **コスト制御**：行動計画生成1日20回／人の上限（429 RATE_LIMITED）
 
**Amazon Cognito（認証）**

- **用途**：ユーザー認証・管理（メール＋パスワード）

- **連携方式**：Amplify Flutter（クライアント）、JWT検証（サーバー）
 
**Amazon SNS（Push通知）**【準備のみ】

- **用途**：iOS／Androidプッシュ通知

- **対応プラットフォーム**：iOS（APNS）、Android（FCM）

- **備考**：Windows Webは対象外、本リリースは配信なし（設定入口のみ）

## 4.4 監視・運用
 
### 4.4.1 監視設定
 
基本的なCloudWatch監視を実施する。監視対象は以下のとおり。
 
- ALB 5xxエラー率

- AI連携基盤レイテンシ（p95）

- CPU使用率・メモリ使用率

- レスポンス時間

- 従量課金サービスの呼び出し量・コスト
 
**コスト・利用量監視（従量課金対策）**

- CloudWatch Billing Alarm によるAWS全体の月次コスト監視

- 行動計画生成：1人あたり1日20回上限（429 RATE_LIMITED）

- Bedrock／Google Maps／乗換案内APIの呼び出し量メトリクス監視

- Cost Explorer連動
 
詳細な閾値設定は運用開始後の実績を踏まえて調整する。アラート通知はSNS経由で行うが、専任の一次対応者・エスカレーションフローは設けず、CloudWatch Alarmsによる通知のみとする。

### 4.4.3 バックアップ・災害対策
 
データベースバックアップはAurora自動バックアップ（保持期間7日）を基本とする。クロスリージョン複製等の追加の災害対策については別途検討とする。RPO／RTOは24時間以内（有人対応前提の軽微保守体制）とする。

## 4.5 開発・デプロイ環境
 
### 4.5.1 環境構成
 
開発、検証、本番の各環境を以下に定義する。本番／検証／開発の3環境を想定する。デプロイはAWS CDKによるIaCとし、ソースzipのS3アップロードを起点として自動デプロイする。
 
**デプロイパイプライン**

- ソースzip → S3 → CodePipeline → CodeBuild → ECR → ECS（ローリング／Blue-Green）

- Flutter Web成果物はS3＋CloudFrontへ配信
 
**開発環境**

- **構成**：シングルAZ、最小構成

- **用途**：開発・単体テスト

- **更新頻度**：随時
 
**検証環境**

- **構成**：本番同等構成（Multi-AZ）

- **用途**：結合テスト、受入テスト

- **更新頻度**：リリース前
 
**本番環境**

- **構成**：冗長化構成（Multi-AZ、ALB／ECS Fargate／Aurora）

- **可用性**：AWS標準SLA準拠。サービス提供時間帯（5:00〜1:00）内で稼働率99.0%程度を目安とする（計画停止・保守作業を除く）

- **サービス提供時間帯**：5:00〜1:00（翌日1時まで。電車の運行時間帯に合わせる。1:00〜5:00はメンテナンス可能）

- **バックアップ**：日次自動（保持7日）
 
**表：環境構成**
 
```

環境	構成	用途	可用性

開発	シングルAZ	開発・単体テスト	通常稼働

検証	Multi-AZ	結合・受入テスト	本番同等

本番	Multi-AZ（冗長化）	本番運用	AWS標準SLA準拠（提供時間帯内 稼働率99.0%目安）

```
 
**Auto Scaling方針**

- ECS Fargateは当面1サービス・最小構成1〜2タスクとし、Auto Scalingを有効化する
