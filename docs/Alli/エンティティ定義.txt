# エンティティ定義

## 概要

本システムは、外出予定を自然文で入力することで、出発から帰宅までの行動計画を自動生成・提示するAIエージェント型アプリケーションである。主要なエンティティは、ユーザー（User）、行動計画（Plan）、行動項目（PlanItem）、スロット評価（SlotEvaluation）、AI対話履歴（AgentSession）、ルーティン（Routine）、メモ（Memo）、カレンダー連携（CalendarIntegration）、カレンダー予定キャッシュ（CalendarEvent）、出発検知記録（DepartureLog）、ポイントプログラム（PointProgram）の11個である。

## 未確定事項

- [x] 乗換案内APIの契約形態・精度が未確定（リスク項目）

  **回答（2026-08-31）**:
  - **契約形態**: 第一候補は **Ekispert API for Amazon（買い切り型）** とする（見積書・詳細設計の方向性）。NAVITIME等の企業向け直接契約は小規模利用にはハードルが高く、代替検証をリスク項目として継続管理する。
  - **用途**: 乗換経路検索、駅名サジェスト（GET /api/geo/station-suggestions）、駅出口・乗車位置情報の取得（AI連携基盤 TransitRouteTool / StationExitTool 経由）。
  - **精度・可用性**: 商用契約締結および結合試験フェーズで、主要利用エリア（首都圏等）における経路精度・駅出口情報の取得可否を検証する。API返却値に不足がある場合は、確認質問または徒歩ルート（Google Maps Routes）で代替し、AI推測のみの駅名・出口は提示しない（ハルシネーション対策）。
  - **残リスク**: 契約条件・API呼び出し上限・運行情報連携の精度は、開発初期のPoC完了時点で再評価する。

- [x] 音声認識サービスの具体的なサービス名が未確定

  **回答（2026-08-31）**:
  - **方針（確定）**: クライアントOS標準の音声認識APIは使用しない。録音データをサーバーへアップロードし、**サーバー側でテキスト化**する（要件定義書・ヒアリングシート確定）。
  - **本リリースの扱い**: **実装準備のみ**（Feature Flag OFF）。POST /api/speech/transcribe はAPIスタブとして骨格のみ提供し、UI入口（音声入力ボタン）は disabled 表示。
  - **具体サービス**: **Amazon Transcribe 等を第一候補**とするが、選定は本リリーススコープ外。準備フェーズ完了時または次フェーズで、対応言語（ja-JP）、レイテンシ、コスト、1分/2MB程度の上限を基準に確定する。
  - **補足**: 音声録音ファイルはテキスト化完了後に**即時破棄**し、永続保存しない（要件定義書 3.2.2）。

- [x] カレンダー連携のトークン管理（Secrets Manager ARN）の妥当性確認が必要

  **回答（2026-08-31）**:
  - **結論**: OAuthトークン本体を **AWS Secrets Manager** に保持し、Aurora（external_integrations）には **メタデータのみ** を保存する方針は **妥当**（要件定義書 3.2.2・DB設計 4.2 準拠）。
  - **IF／DB上の属性**: 本エンティティ定義の `access_token_secret_arn` / `refresh_token_secret_arn` は、物理設計では **`secret_name`（シークレット名）1件** に集約する。命名例: `integration/{user_id}/{provider}`。ARNの直持ちは行わず、Secrets Manager SDK は secret_name で参照する。
  - **Aurora側で保持する項目**: provider、status（CONNECTED / DISCONNECTED / ERROR）、secret_name、scope、connected_at、last_synced_at、last_error、created_at、updated_at。
  - **トークン有効期限**: OAuthプロバイダから取得した expiry は Secrets Manager 内のトークンJSONに含め、必要に応じて refresh 処理で更新する。Auroraには last_synced_at のみキャッシュ可。
  - **退会時**: DELETE /api/account 実行時に Secrets Manager 上の `integration/{user_id}/*` を prefix 削除する（APIサービス詳細設計 7.2 準拠）。

- [x] 外部サービス連携に必要な属性（cognito_user_id、external_account_id、access_token_secret_arn等）の妥当性確認が必要

  **回答（2026-08-31）**:
  - **cognito_user_id**: **妥当**。ただし integer 型の User.id とは別に、全テーブルの `user_id` は **Cognito sub（string）** として統一する（DB設計・JWT検証方針）。エンティティ定義上の `cognito_user_id` は `user_profiles.user_id` に相当し、APIレスポンスでは JWT から解決するため **クライアントへ返却しない**。
  - **external_account_id**: Google / Outlook 連携時に外部側のアカウント識別子が必要だが、**APIレスポンスおよび Aurora カラムとしては必須にしない**。Secrets Manager 内のトークンJSON、または OAuth 連携完了時の内部メタデータとして保持する。プロバイダごとに1アカウントのみ（UNIQUE user_id + provider）の制約で十分。
  - **access_token_secret_arn / refresh_token_secret_arn**: **概念は妥当だが、物理設計では secret_name 1件に集約**（上記カレンダー連携の回答参照）。IF仕様書・OpenAPI スキーマでは `secretName` をサーバー内部属性とし、外部公開しない。
  - **その他の外部連携属性**:
    - Google Maps APIキー: サーバー用・クライアント用（3種）を Secrets Manager / ビルド設定で分離管理（要件定義書 4.3.1）。
    - 乗換案内APIキー: サーバー用 Secrets Manager 管理。
    - Bedrock / Cognito: AWS SDK 経由。IFエンドポイントとしては設計しない（Cognito 認証は Amplify Flutter 直接利用）。

## 正規化対応の説明

本エンティティ定義は、以下の正規化観点で確認を行いました。

### 観点1：複数エンティティ間でのデータ同期リスク

行動計画（Plan）と行動項目（PlanItem）、スロット評価（SlotEvaluation）の関係において、ステータス管理の責務を明確に分離しました。行動計画全体のライフサイクル（生成中、確認質問中、完了、エラー）は親エンティティであるPlanのstatusで一元管理し、子エンティティであるPlanItemやSlotEvaluationには独自のステータスを持たせない設計としています。これにより、複数エンティティ間でのステータス同期の問題を排除しています。

SlotEvaluationのis_evaluatedフラグは、AIの評価プロセスの監査ログとして独立した目的を持つため、Planのstatusとは別に保持しています。

### 観点2〜5：その他の正規化観点

- 繰り返し属性の分離：frequently_used_stationsやchecked_linesは配列型で適切に管理されており、問題ありません。
- 部分関数従属・推移的関数従属：各エンティティは単一の主キー（id）に対して全属性が完全関数従属しており、第2正規形・第3正規形を満たしています。
- 冗長なリレーション：N:N関係は適切に中間テーブルで解決されており、業務上必要な直接的なFK（user_id、plan_id等）は維持しています。

以上の確認により、本エンティティ定義は正規化の観点から問題がないことを確認しました。
